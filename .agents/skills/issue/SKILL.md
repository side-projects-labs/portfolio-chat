# Issue

이슈를 만들 때는 이 절차만 사용한다. 본문 형식을 임의로 바꾸지 않는다. 이슈 생성은 사용자가 요청했을 때만 한다.

## 절차

```
- [ ] 1. 범위 확인: 사용자가 말한 작업만 이슈로 만든다. 다른 작업으로 바꾸지 않는다
- [ ] 2. 제공된 요구와 관련 이슈·댓글을 읽고 본문 작성에 필요한 최소한의 코드·계약만 확인한다. 이슈 요청을 구현·수정·커밋 작업으로 확대하지 않는다
- [ ] 3. 담당자 계정 확인: gh api user --jq .login
- [ ] 4. `.github/ISSUE_TEMPLATE.md`의 절을 채운다. 예상, 변경범위, 코드, 1급 시민, 불변조건, TDD 기준 테스트 조건은 목록이다. 비어 있거나 안내 주석이 남아 있으면 만들지 않는다
- [ ] 5. 1급 시민 규칙을 확인한다. 예상의 동작이 1급 시민 목록과 테스트 조건에 없으면 만들지 않는다
- [ ] 6. 제목과 본문이 아래 문체 규칙을 지키는지 확인한다
- [ ] 7. 완성한 본문을 임시 파일로 검토한 뒤 gh issue create --repo <owner/repo> --assignee <login> --title <title> --body-file <path>로 생성한다
- [ ] 8. 조직 `side-projects-labs`의 GitHub Project `@NoCodeBuild`에 이슈를 넣고 Status를 `Todo`로 둔다
- [ ] 9. 본문·담당자·요청된 상하위 관계·Project/Status 반영을 조회로 검증한다. 완료 시 URL을, 부분 실패 시 URL과 미완료 항목을 함께 보고한다
```

저장소는 현재 git remote의 GitHub 저장소다. 이미 같은 작업의 열린 이슈가 있으면 새로 만들지 않고 그 URL을 알린다.

`gh issue develop`로 브랜치를 연결하지 않는다. 본문에 `Fixes`, `Closes`, `Resolves`를 쓰지 않는다. 관련 이슈는 배경에 `#번호`만 적는다. 사용자가 닫으라고 하기 전에는 이슈를 닫지 않는다.

## 요구사항과 설계 근거

- 현재 요청과 관련 이슈 본문·댓글에서 실행 가능한 요구사항을 빠짐없이 수집한다. 각 요구를 포함·후속 작업·범위 밖 중 어디에 두었는지 정리하고 제외 이유를 적는다.
- 확인된 현상·사용자 요구와 미확인 원인·구현 후보를 구분한다. 미확인 내용을 확정 사실이나 필수 구현으로 만들지 않는다. 핵심 요구가 충돌해 범위를 정할 수 없으면 생성 전에 필요한 정보만 확인한다.
- 예상의 각 동작을 `1급 시민`과 `TDD 기준 테스트 조건`에 연결하고, 변경범위에는 필요한 구현·검증 순서를 적는다.
- `코드`에는 구현 파일과 테스트 파일을 구분한다. 확인하지 않은 경로는 존재하는 파일처럼 쓰지 않고 후보와 확인 단계를 적는다. portfolio2에서 옮기는 작업이면 원본 경로를 적는다.
- `불변조건`에는 유지할 데이터·권한·공개 노출 계약과 확인 근거를 적는다. 공개 저장소이므로 비밀값·프롬프트·대화 내용의 공개 여부를 반드시 다룬다.
- 문서·설정 전용 작업은 테스트를 억지로 만들지 않고 생략 이유와 링크·경로·계약·민감정보 확인 같은 대체 검증을 적는다.

## 생성과 관계 검증

- 현재 저장소에 설정된 프로젝트 로컬 GitHub 인증이 있으면 사용한다. 담당자는 해당 활성 계정으로 지정하며 다른 저장소의 Project 번호·필드 ID를 복사하지 않는다.
- 생성 전에 제목, 본문, 담당자, 요청된 parent와 Project 대상이 현재 요청과 일치하는지 검토한다. 본문 미리보기만 요청받았으면 게시하지 않는다.
- 하위 이슈를 요청받으면 REST sub-issue API(`POST repos/<owner>/<repo>/issues/<parent>/sub_issues`, `-F sub_issue_id=<정수 ID>`)로 연결하고 상위 이슈의 하위 목록에서 확인한다. 본문의 `#번호` 표기만으로 연결 완료로 보고하지 않는다.
- 생성 또는 연결 요청이 불명확하면 먼저 조회로 실제 반영 여부를 확인한다. 관계·Project·Status 처리 실패로 같은 이슈를 다시 생성하지 않는다. 권한이 부족하면 생성된 이슈는 보존하고 URL, 완료 항목, 미완료 항목과 원인을 보고한다.

## Project와 상태

이슈는 조직 `side-projects-labs`의 GitHub Project `@NoCodeBuild`에 넣고 Status 필드로만 상태를 나타낸다. 라벨로 상태를 만들지 않는다. 값은 Project에 있는 옵션만 쓴다.

- 프로젝트 번호, 필드 ID, 옵션 ID는 고정값으로 외워 두지 않고 실행할 때 조회한다
  - `gh project list --owner side-projects-labs`로 `@NoCodeBuild`를 찾는다
  - `gh project field-list <번호> --owner side-projects-labs --format json`으로 Status 필드와 옵션 ID를 얻는다
  - `gh project item-add <번호> --owner side-projects-labs --url <이슈 URL> --format json`으로 넣고, `gh project item-edit`로 Status를 지정한다
- 아직 시작하지 않았으면 `Todo`, 작업을 시작했으면 `In Progress`, 리뷰로 넘겼으면 `In Review`, 끝났으면 `Done`을 쓴다. `Backlog`와 `Blocked`는 사용자가 요청했을 때만 쓴다
- 새 이슈는 `Todo`다. 프로젝트에 넣은 뒤 Status를 비워 두지 않는다

## 1급 시민

배경, 예상, 변경범위, 코드, 1급 시민, 불변조건, TDD 기준 테스트 조건은 이슈의 1급 시민이다. 테스트 조건을 부가 설명, 주석, 구현 뒤에 붙이는 메모로 두지 않는다.

예상, 1급 시민 목록, 테스트 조건은 같은 동작을 가리킨다. 예상에만 있고 1급 시민 목록이나 테스트 조건에 없는 동작이 있으면 이슈를 만들지 않는다.

코드 동작은 그 동작을 검증하는 테스트와 함께 1급 시민이다. 테스트를 구현보다 나중에 적거나 빼면 이슈가 아니다. 문서와 설정만 바꾸는 작업은 테스트를 추가하지 않는 이유와 대신 확인할 방법을 테스트 조건 절에 적는다. 그 예외를 빈 칸으로 두지 않는다.

## 문체

제목과 본문의 문장은 `~습니다` 또는 `~ㅂ니다`로 끝낸다. `~다`, `~한다`, `~했다`, `~이다`로 끝내지 않는다. 한 이슈 안에서 어미를 섞지 않는다. 코드, 식별자, URL, 체크박스 기호는 문장이 아니다. 마침표는 붙이지 않는다.

제목은 작업 한 줄을 문장으로 쓴다. 예: `채팅 입력을 모델에 보내기 전에 길이를 검증합니다`

## 본문

본문은 `.github/ISSUE_TEMPLATE.md`만 채운다. 절을 추가하거나 빼거나 순서를 바꾸지 않는다. 안내 주석은 제출 본문에 남기지 않는다. 예상, 변경범위, 코드, 1급 시민, 불변조건, TDD 기준 테스트 조건은 목록이고 항목마다 `~습니다` 또는 `~ㅂ니다`로 끝낸다. 관련 PR이나 이슈는 배경에 `#번호`로 적는다. 비밀값, 토큰, `.env` 내용은 넣지 않는다.
